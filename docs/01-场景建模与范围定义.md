## 1. 命名规范（强制）

### 1.1 三套命名，不得混用

| 命名空间 | 用途 | 例 | 出现位置 |
|---|---|---|---|
| **中性名** | 场景契约（本文档） | `CreditCardApp`、`USES_DATASOURCE`、`app.datasource.active_connections` | `shared/`、采集层、评测台 |
| **KG 名** | Neo4j 载体 | Label `:CC_CreditCardApp`、关系 `:CC_USES_DATASOURCE`（**大写下划线** + ★ **`CC_` 命名空间前缀**）、属性 `activeConnections`（**不加前缀**） | `scheme1-kg/` |
| **ONTO 名** | RDF/OWL 载体 | `cc:CreditCardApp`、`cc:usesDataSource`（**小驼峰**）、`cc:activeConnections` | `scheme2-onto/` |

> ★ **`CC_` 前缀的由来（`00-` 裁决 13）**：方案1 的图**不是建在空库上**——它装进**已在运行且已有数据**的 Neo4j 5-community 实例（`192.0.2.10` 的 `neo4j-gaussdb`，HTTP 7475 / Bolt 7688），库内已有 **423 节点 / 34 标签 / 37 关系类型** 的 v2 本体图；community 版是**单库**（`SHOW DATABASES` 只有 `neo4j`/`system`），无法用数据库隔离，而标签 `Host`/`Table`/`Session` 与关系类型 `ACCESSES`/`DEPLOYED_ON` 与 v2 图**同名**。故方案1 侧**所有标签与关系类型统一加 `CC_` 前缀**与之**物理共存**；**属性名、端口号、OWL 侧（`cc:`）名字均不变**。

**强制**：中性名 → KG 名 / ONTO 名的映射写在 `shared/mapping/type-map.yaml` 与 `rel-map.yaml`，**是数据不是代码**，可 diff、可审阅。投影器只读这两张表。 ★ `CC_` 前缀**写在映射表里**（`type-map.yaml` / `rel-map.yaml` 的 KG 名那一列，**是数据不是代码**），投影器**不得硬编码标签名**。

### 1.2 编码规范

| 类型 | 模式 | 例 |
|---|---|---|
| 应用 | `APP-<域>` | `APP-CC-PAY`（信用卡支付应用） |
| 实例 | `inst:<type>-<序号>` | `inst:app-cc-pay-0`、`inst:ctr-cc-pay-0` |
| 指标码 | `<层>.<对象>.<度量>` | `app.datasource.active_connections` |
| 故障模式 | `FM-<层>-<对象>-<现象>` | `FM-APP-POOL-EXHAUSTED` |
| 规则 | `RULE-<两位序号>` | `RULE-07` |
| 结论 | `F-<三位序号>` | `F-012` |
| 动作 | `ACT_<大写下划线>` | `ACT_INCREASE_POOL_SIZE` |
| 连接 | `JDBC-<应用>-<序号>` | `JDBC-CC-PAY-1` |

**指标码是投影器与规则之间的唯一契约**：规则只引指标码，投影器负责把它落成载体原生属性。这样"新增一条故障链"只改规则 + 映射表，不改投影器代码。

**`JdbcDataSource`（应用侧连接池）与 `DatabaseSessionPool`（数据库侧会话池）的互斥性**：两者语义互斥（§5.1），必须在两方案中都以“能表达互斥”的方式建成不同对象。载体侧：
- KG：两个独立 Label，无共同 Label（**靠约定互斥**）
- ONTO：`cc:JdbcDataSource rdfs:subClassOf cc:ConnectionPool`、`cc:DatabaseSessionPool rdfs:subClassOf cc:ConnectionPool`、且 `cc:JdbcDataSource owl:disjointWith cc:DatabaseSessionPool`（**靠公理互斥，可被一致性检查验证**）。★ 2026 契约修正：原互斥对上的第三个名字 `AppDataSource` 已删除（无任何关系/指标/故障模式引用它 ⇒ 投影后产生孤立节点，撞 G5 门禁）。

| `Evidence` | 观测证据（**派生 / `annotation: true`**） | `recordId` `metricCode` `status` `rawValue` `rawUnit` `reason` `probe` `capturedAt` | — |

★ **M1.5c（2026-10-05，用户裁定 U-Q = 方案 A）**：`Evidence` 是**派生类型**——**层为 `null`**（`layer: null`，**不得**写 `layer` 属性）、`annotation: true`、`key_attrs: [recordId]`。它**不出现在 CCF 的 `objects[]`**，而由投影器从 `observations[]` **每条观测派生一个节点、不聚合**（真机 167 条观测 ⇒ 167 个证据节点）。属性名 ← CCF 观测字段路径的派生规则写在 `shared\mapping\type-map.yaml#observation_projection.evidence`（**是数据不是代码**）；`capturedAt` 按 `xsd:dateTime`、其余 7 个按 `xsd:string` 收敛 ⇒ 两侧落盘字面量同形；源字段缺失或为 `null` ⇒ **不写该属性**（两侧一致）。

## 3. 关系目录

| 中性关系 | 从 → 到 | 基数 | 语义 |
|---|---|---|---|
| `HAS_APP_INSTANCE` | `CreditCardApp` → `AppInstance` | 1:N | 应用有实例 |
| `EXPOSES` | `CreditCardApp` → `AppEndpoint` | 1:N | 应用暴露端点 |
| `RUNS_IN` | `AppInstance` → `Container` | N:1 | 实例跑在容器内 |
| `DEPLOYED_ON` | `Container` → `Host` | N:1 | 容器在宿主机上 |
| `USES_DATASOURCE` | `AppInstance` → `JdbcDataSource` | N:1 | 实例使用数据源 |
| `CONNECTS_TO` | `JdbcDataSource` → `GaussDBCluster` | N:1 | 数据源连到集群 |
| `RESOLVES_TO` | `JdbcDataSource` → `GaussDBInstance` | N:1 | 运行时解析到具体实例 |
| `HAS_DB_INSTANCE` | `GaussDBCluster` → `GaussDBInstance` | 1:N | 集群含实例 |
| `HOSTS` | `Host` → `GaussDBInstance` | 1:N | 宿主机承载 DB 实例（自建场景） |

| `HAS_EVIDENCE` | `*` → `Evidence` | 1:N | 对象 → 它自己的观测证据（★ **派生**：`asserted_in_ccf: false`、`cross_layer: false`、`derived_from: observations`；**域不受限**，任何运维对象都能挂证据） |

> ★ **契约计数**（`shared/model/topology.yaml` **v1.1.0**）：`type_count: 14` = 12 个可实例化类型（本目录 §2.1–§2.3 逐层列出）+ 1 个抽象 `ConnectionPool`（不在本目录单列，见 `04-` §3）+ 1 个**派生证据型** `Evidence`（§2.4，`layer: null`）；`relation_count: 15` = 14 条由 CCF `relations[]` 断言（`asserted_in_ccf: true`）+ 1 条**派生** `HAS_EVIDENCE`（由 `observations[]` 逐条派生）。★ M1.5c 前为 13 类型 / 14 关系；`max_hop_depth` 由 9 升至 **10**（`Table → 其 Evidence 节点` 再 +1 跳）。

> ★ **M1.6 注（2026-10-06）**：本表 `app.*` / `container.*` 两行与上条结论均为 **M1.6 之前**的状态；两层探针**已实现并真机实测**，通道**不是 SSH 而是只读 HTTP**（container → Prometheus NodePort `30090`；app → 应用 `GET /health` NodePort `30085`），见 `02-` **§2.5**。

### 4.1 两个新采集器（N1 / N2）的实现边界

| | N1 container | N2 app |
|---|---|---|
| 采集通道 ★ | **SSH**（用户裁定 m01249 / `00-` 裁决 11）。原「首选 K8s API：`kubelet` `/stats/summary` + cAdvisor `/metrics`」**已废弃** | **SSH**（同上）。原「Micrometer：`GET /actuator/prometheus`，退路 `/actuator/metrics` JSON」**已废弃** |
| 通道内读什么（施工期定） | cgroup v2 直读（`/sys/fs/cgroup/.../cpu.stat`、`memory.peak`、`memory.events`）/ `crictl` / `docker stats` | JMX `java.lang:type=Memory`/`GarbageCollector`；本机 loopback HTTP；应用日志解析 |
| 覆盖指标 | `container.cpu_usage_ratio` / `cpu_throttled_periods` / `mem_working_set_mb` / `oom_kill_total` / `restart_total` / `status` | `app.uptime_s` / `heap_used_ratio` / `gc_pause_ms` / `thread_count` / `endpoint.p99_ms` / `error_rate` / `qps` / `datasource.*` |
| 强制契约 | 两者**只走既有 `ProbeResult` 协议**（`service/probes/__init__.py`），**绝不碰** `collect_api` 组合入口 | 同左 |
| ⚠ 硬性约束 | 新探针必须沿用生产者 A 的 `_make_fact()` 六键形态（**含 `obj_type`**），不得使用 `collect_api._to_facts()` 内嵌 `add()` 的五键形态（**无 `obj_type`**）——见 `02-` §3.3 勘误 | 同左 |

> ★ **M1.6 注（2026-10-06）**：本表「采集通道 ★」与「通道内读什么（施工期定）」两行为 **M1.6 之前**的判定；实际落地 = **只读 HTTP**（同上），**未采用 SSH / JMX / cgroup v2 直读 / Micrometer**。见 `02-` **§2.5**。

## 5. 故障模式与因果边

### 5.1 建模形态（三形态，沿用 `gdo-v3` 已验证设计）

| 形态 | 语义 | 例 |
|---|---|---|
| **因果边**（无条件） | A 必然导致 B | `FM-DB-SLOW-QUERY` → `FM-APP-POOL-EXHAUSTED` |
| **条件因果边**（带前提） | 仅当某指标满足条件时 A 导致 B | `FM-HOST-CPU-CONTENTION` → `FM-CTR-THROTTLED`，前提 `host.cpu_usage_ratio > 0.9` |
| **相关边**（对称、非因果） | A 与 B 常共现，**不参与因果收敛** | `FM-DB-SLOW-QUERY` ↔ `FM-DB-LOCK-WAIT` |

**必须继承的两条经验**（来自 `gdo-v3` 的实测教训）：
1. **不声明传递性**。`gdo-v3` 的因果图 16 节点中 13 个同属一个强连通分量，传递闭包在环图上对“排序”无定义，因此**刻意不声明 `owl:TransitiveProperty`**。本项目的因果图同样成环（**实测唯一有向环 = `FM-APP-POOL-EXHAUSTED` ↔ `FM-APP-ENDPOINT-SLOW`，即 E5 + E6**），必须同样处理。
2. **区分"共现"与"因果"**。共现边只作呈现，绝不参与根因收敛——否则根因集合会被伴生故障撑爆。

### 5.2 故障模式清单（本期 14 条，覆盖 7 条链）

| 编码 | 名称 | 层 | 组件类型 | 关键判据指标 |
|---|---|---|---|---|
| `FM-APP-POOL-EXHAUSTED` | 应用侧连接池耗尽 | App | `JdbcDataSource` | `app.datasource.active_connections ≈ maxPoolSize` ∧ `app.datasource.pending_threads > 0` |
| `FM-APP-DS-CONNECT-FAIL` | 数据源连接建立失败 | App | `JdbcDataSource` | `app.datasource.connect_fail_total` 增长 ∧ `connect_latency_ms` 超时 |
| `FM-APP-ENDPOINT-SLOW` | 应用端点响应劣化 | App | `AppEndpoint` | `app.endpoint.p99_ms > sloP99Ms` |
| `FM-APP-INSTANCE-RESTART` | 应用实例重启 | App | `AppInstance` | `app.uptime_s` 归零 |
| `FM-APP-HEAP-PRESSURE` | 应用堆内存压力 | App | `AppInstance` | `app.heap_used_ratio > τ` ∧ `app.gc_pause_ms` 升高 |
| `FM-CTR-OOM-KILLED` | 容器 OOM 被杀 | Runtime | `Container` | `container.oom_kill_total` 增长 ∧ `restart_total` 增长 |
| `FM-CTR-CPU-THROTTLED` | 容器被 CPU 限流 | Runtime | `Container` | `container.cpu_throttled_periods` 增长 |
| `FM-CTR-NET-UNREACHABLE` | 容器网络不可达 | Runtime | `Container` | （应用侧连接失败 + 容器网络异常，需双侧证据） |
| `FM-HOST-CPU-CONTENTION` | 宿主机 CPU 争抢 | Runtime | `Host` | `host.load1` 高 ∧ `host.cpu_usage_ratio > τ` |
| `FM-HOST-MEM-PRESSURE` | 宿主机内存紧张 | Runtime | `Host` | `host.mem_available_ratio < τ` |
| `FM-DB-SLOW-QUERY` | 数据库慢查询 | Data | `Query` | `db.query.mean_exec_ms > τ` |
| `FM-DB-SESSION-POOL-FULL` | 数据库会话池耗尽 | Data | `DatabaseSessionPool` | `db.pool.session_used_ratio > τ` ∧ `conn_rejected_total` 增长 |
| `FM-DB-LOCK-WAIT` | 数据库锁等待 | Data | `Session` | `db.session.wait_event ∈ {LockMgrLock, transactionid, relation, tuple}` |
| `FM-DB-INSTANCE-DOWN` | 数据库实例故障/切换 | Data | `GaussDBInstance` | `db.instance.up = 0` ∨ `db.cluster.switchover_total` 增长 |

> **契约口径（`fault-modes.yaml` v1.0.3 新增，裁定 X-5 / X-7 / X-10）** —— `shared\model\fault-modes.yaml` 是判据的唯一权威，下列三条必须逐字落地到两侧载体：
> ① **分组语义**：`detect` 可含并列的 `all_of` / `any_of` 两组；组内 `all_of` **全部**成立、`any_of` **至少一条**成立；**组间为 AND**；缺省组视为中性成立。**禁止组间 OR** —— 否则 `all_of` 失去「必需条件」含义，单条弱证据（如仅 `app.uptime_s` 下降）即可触发。
> ② **谓词语义**：`increased` = `observation.delta` 为正、`decreased` = `observation.delta` 为负 —— **需要窗口基线**（`shared\model\ccf.schema.json` 的 `$defs.observation.delta` / `deltaWindowS`，均为**可选**字段）。`delta` 缺失 ⇒ 该条目 `unjudgeable`：**既不成立也不证伪**，按 WARN「待标定/不可机判」处理并登记 `shared\model\zero-instance-ledger.yaml`，**严禁静默当作 false**。
> ③ **词表边界**：完整故障词表 = 本表 **14 条** detect 模式 ∪ `shared\model\causal-edges.yaml#leaf_root_causes[].subtype` 声明的**排除法叶子**（当前 1 条 `FM-APP-AUTH-INCOMPATIBLE`，`detection_mode: exclusion`，其权威仍在 `causal-edges.yaml`）⇒ 共 **15 码**；任何跨契约引用（`leaf_root_causes` / `discriminators` / 规则载体）必须可解析，由门禁 **G18** 校验。

## 6. 七条故障链的详细定义（用例骨架）

每条链给出：**现象 → 传播路径 → 判据 → 该链的建模难点 → 区分度**。

### F1 · 应用侧连接池耗尽 → 交易超时
- **现象**：交易 P99 劣化，应用日志 `Connection is not available, request timed out`
- **传播**：`FM-APP-POOL-EXHAUSTED` →(E5)→ `FM-APP-ENDPOINT-SLOW`
- **判据**：`app.datasource.active_connections` 贴顶 ∧ `app.datasource.pending_threads > 0`，且 `db.pool.session_used_ratio` **正常**
- **难点**：必须与 `FM-DB-SESSION-POOL-FULL` 区分。**判据是"数据库侧正常"**——即需要靠"某个指标正常"来定罪，这是**否定性证据**。
- **区分度**：中。两方案都能做，但 KG 侧写模式容易漏掉"数据库侧正常"这个条件。

### F2 · GaussDB 慢查询 → 会话占用 → 应用池耗尽（★核心跨层用例）
- **现象**：交易超时，应用侧池满，但**应用配置没变、流量没变**
- **传播**：`FM-DB-SLOW-QUERY` →(E1)→ `FM-APP-POOL-EXHAUSTED` →(E5)→ `FM-APP-ENDPOINT-SLOW`
- **判据**：`db.query.mean_exec_ms > τ` ∧ `db.session.query_elapsed_s` 长 ∧ `app.datasource.active_connections` 贴顶
- **难点**：**方向反直觉**——症状在最上层，根因在最下层，且中间隔着 3 跳。需要沿 `Query → Session → DatabaseSessionPool → JdbcDataSource → AppInstance` 逆向追溯。
- **区分度**：**高**。这是"跨层"的本体论价值所在。

### F3 · 宿主机争抢 → 容器限流 → 应用变慢
- **现象**：应用 P99 上升，容器 CPU 用量正常，宿主机 load 高
- **传播**：`FM-HOST-CPU-CONTENTION` →(E7,条件)→ `FM-CTR-CPU-THROTTLED` →(E8)→ `FM-APP-ENDPOINT-SLOW`
- **判据**：`host.cpu_usage_ratio > 0.9` ∧ `container.cpu_throttled_periods` 增长 ∧ `container.cpu_usage_ratio` **可能不高**
- **难点**：**"容器指标正常但被限流"**。若只看容器，结论会是"应用自身慢"。必须**跨层对照**（Host vs Container）。
- **区分度**：**高**。条件因果边（E7）的建模是两方案的直接对比点：KG 侧条件写在关系属性还是查询里？ONTO 侧能否用 SWRL/规则表达条件？

### F4 · 容器 OOMKilled → 应用重启 → 交易失败
- **现象**：交易间歇性失败，应用实例重启
- **传播**：`FM-HOST-MEM-PRESSURE` →(E9,条件)→ `FM-CTR-OOM-KILLED` →(E10)→ `FM-APP-INSTANCE-RESTART` →(E11)→ `FM-APP-ENDPOINT-SLOW`
- **判据**：`container.oom_kill_total` 增长 ∧ `app.uptime_s` 归零
- **难点**：**证据源唯一**——容器事件（`container.oom_kill_total`）。宿主机指标可能完全正常（若容器 limit 小而非宿主机紧张）。因此 E9 的**条件**与 E12 的**条件**是两条不同的因果路径（宿主机紧张 vs 容器 limit 过小）。
- **区分度**：**高**。同一现象两条因果路径，考验多根因/路径排序能力。

### F5 · JDBC 驱动/认证不兼容 → 连接建立失败（★难点用例）
- **现象**：应用完全连不上数据库，报认证/协议错误
- **传播**：`FM-APP-DS-CONNECT-FAIL` →(E18)→ `FM-APP-ENDPOINT-SLOW`
- **判据**：`app.datasource.connect_fail_total` 增长 ∧ `connect_latency_ms` 立刻失败（不是超时）∧ 数据库侧 `db.instance.up = 1` ∧ 容器网络正常
- **难点**：**叶子根因，靠排除法定罪**。必须能表达"数据库正常 ∧ 网络正常 ∧ 配置异常"。
  - 真实来源：`upstream-ops-agent` 实测踩过 Kernel 507 专有 SASL——`libpq` 报 `none of the server's SASL authentication mechanisms are supported`。
- **区分度**：**极高**。排除法需要**否定性推理**，OWL 的封闭世界假设（CWA，配 SHACL）与 LPG 的"查不到就是没有"语义不同，这会暴露两方案在**缺省推理**上的本质差异。

### F6 · 容器网络/DNS 异常 → 连不上 DB
- **现象**：应用连不上数据库，报连接超时（非认证错误）
- **传播**：`FM-CTR-NET-UNREACHABLE` →(E13)→ `FM-APP-DS-CONNECT-FAIL` →(E18)→ `FM-APP-ENDPOINT-SLOW`
- **判据**：`connect_latency_ms` 超时 ∧ 从容器内到 DB 的网络不可达 ∧ DB 侧正常
- **难点**：与 F5 的区分点在**失败模式**（超时 vs 立即拒绝）与**失败位置**（网络 vs 认证）。二者共享同一出口节点 `FM-APP-DS-CONNECT-FAIL`，**必须靠叶子证据区分**。
- **区分度**：**高**（与 F5 构成"同症状不同根因"的一对）。

### F7 · GaussDB 实例故障 → 主备切换 → 短时中断（★难点用例）
- **现象**：交易出现瞬时错误尖峰，随后自动恢复
- **传播**：`FM-DB-INSTANCE-DOWN` →(E14)→ `FM-APP-DS-CONNECT-FAIL` →(E18)→ `FM-APP-ENDPOINT-SLOW`
- **判据**：`db.instance.up = 0` ∧ `db.cluster.switchover_total` 增长 ∧ 应用侧错误尖峰的时间窗**与切换时间对齐**
- **难点**：**时间对齐**。采集是快照式的（`sampled_at`），若两方案的模型不能表达"两个事实在时间窗内共现"，这条链就推不出来。
- **区分度**：**极高**。这考验的是**知识载体的时间建模能力**：
  - KG：时间只能作为属性/关系属性，时间窗查询靠 Cypher 的 `WHERE` 过滤
  - ONTO：可用 `prov:Activity` / 时间区间（Allen 区间代数 / OWL-Time），但**既有 `onto-ops-agent` 完全没有时间本体** ⇒ 两方案都需要新建，属于增量对比。
