## 0. 一句话结论

1. **Agent 层没有取代建模层，而是把建模层变成了工具面。** 让 LLM 直接读遥测（metric/log/trace 塞进上下文）在公开评测上定位能力很弱；行业收敛到"LLM 出假设与查询 ⇒ 确定性模型/图做校验与排序 ⇒ 工具面返回有界证据"。本项目 `00-` 裁决 1（LLM 出假设与查询、知识库做确定性校验）与裁决 D-7/D-8（单 Agent + 工具面 + MCP）**正落在这条主线上**，不需要改。
2. **本项目的真正瓶颈不在 agent，也不在用例数量，而在"可机判模式只有 4/14"与"输入不全时判据机不降级"这两件事上。** 前者是采集层问题（`06-` §6.6.6 已指出三条解药全落采集层），后者是 v1 报告过度声称的机制性原因（`10-` §9.4 已作为纪律记下，但**尚未机检化**）。外部调研的价值主要在于为这两件事提供**参照系与外部效度**，而不是提供新的建模范式。
3. **本文对行业最有信息量的一条**：本项目**尚未测**的方案3（不给查询语言、仅靠拓扑工具引导）**恰好比已测的 KG-Q/ONTO-Q 更接近 2024 之后的行业主流**（MCP 式工具编排，不让 LLM 写 DSL）。也就是说，本批正式跑测的是"LLM 写查询语言"这条**行业正在退潮**的路线 ⇒ 方案3 三臂的单独批次，其对外说服力可能高于本批。

## 1. 坐标系：跨层 RCA 的三段切分

业界谈"跨层故障根因分析"时经常混谈三件不同的事，分开才看得清各自成熟度：

| 段 | 它回答的问题 | 业界成熟答案 | 本项目的落点 |
|---|---|---|---|
| **① 事实底座** | 跨层对象/关系/指标怎么统一表示 | OpenTelemetry 语义约定、Elastic Common Schema、TMF SID、ITU-T X.733 | `shared\model\ccf.schema.json`（**CCF 是自研版**，见 §3） |
| **② 建模范式** | 从事实推出"谁导致谁" | 六个范式（见 §2） | `shared\model\causal-edges.yaml` + `topology.yaml` + `发findings.yaml` + 两侧规则库 |
| **③ 决策与行动** | 谁出假设、查证、定界、走门控 | **Agent 时代的新增层**：LLM 编排 + 工具面 + 门控三档 | Dify ReAct + `cc_*` 工具面 + 裁决 5 门控（0.70/0.40） |

> ★ 六个范式（§2）之间**不是替代关系**。工业界成品几乎都是"P1 作骨架 + P3 作知识 + P4 作信号 + P5 作高频根因 + agent 作编排"的组合。**不要**把某一家开源项目当"完整答案"采购式对标。

## 2. 六个建模范式

### 2.1 P1 · 拓扑/依赖图 + 传播打分 ★（工业界事实上的主流，成熟度最高）

- **方法**：先有图（CMDB / 服务依赖 / 调用链 / 资源承载链），再在图上做异常传播与归因排序——随机游走、PageRank 变体、可疑度传播、条件概率传播（贝叶斯网络）、Shapley 式贡献分解。
- **它的根基很老也很硬**：电信网管的**故障传播模型 + 事件关联 codebook**（Yemini 等 1996；Steinder & Sethi 2004 的网络故障定位综述 ⚠[转引年份]）——"跨层"这件事最早就是被电信网管解决的，不是被微服务解决的。
- **微服务方向的学术代表**（用于对标 `causal-edges.yaml` 的边语义）：

| 工作 | 机制一句话 | 置信 |
|---|---|---|
| `MicroRCA`（2019） | 服务调用图 + 异常传播打分定位根因 | ✅ |
| `MicroRank` | trace 图上的 Personalized PageRank | ⚠ |
| `TraceRCA` | trace 上的可疑度传播，显式处理**多根因** | ⚠ |
| `Eadro`（MSR 2022） | log/metric/trace 多模态 + 共同模式聚类 | ⚠ |
| `Nezha`（ASPLOS 2023） | **差分日志语义**（比较正常/异常两条 trace 的日志差异）跨服务定位 | ⚠ |
| `CausalRCA` / `RCD` | 因果图 + 对比/因果学习做微服务 RCA | ⚠ |

- **开源观测侧实现**（这些才是"成熟开源项目"的答案）：

| 项目 | 与本项目的关系 | 置信 |
|---|---|---|
| **Apache SkyWalking** | 拓扑自动发现 + eBPF Rover + 告警规则 + 慢 SQL 追踪；**拓扑模型可直接读代码学** | ✅ |
| **DeepFlow**（云杉网络） | eBPF 全栈可观测 + 自动依赖图 + 跨层指标关联 | ✅ |
| **Coroot** | eBPF + 自动服务图 + **每个服务自带健康检查/RCA 视图**；结构与你"对象→证据→结论"最像 | ✅ |
| **Cilium Hubble** | 网络/服务依赖图（网络层证据源） | ✅ |
| **Grafana Beyla** | eBPF 自动埋点（无侵入取应用层信号） | ✅ |
| **Pixie** | eBPF 可观测（已并入 New Relic） | ⚠ |

- **与本项目的直接关系**：`01-` §3.1 的 9 跳拓扑 + `causal-edges.yaml` 的 18 条边**就是这个范式的骨架**。但本项目目前的推理形态以**规则命中**为主（`RULE-xx` → `F-xxx`），而**缺"沿边传播打分"这一算子**。
- **可迁移点（低成本、落主判据）**：规则给**候选**，传播给**排序**。规则命中在"多根因/共因"下会系统性退化，而 `06-` §2.1 规定"多候选只取第一个计入 `root_cause_accuracy`" ⇒ **没有传播打分，Top-1 命中率会被规则输出顺序支配**。详见 `docs\项目下一步优化方案建议.md` 的 P2。

### 2.2 P2 · 因果发现与结构因果模型（SCM）

- **方法**：`PC / FCI / GES / NOTEARS / LiNGAM`（含 `VAR-LiNGAM` 处理时序）、do-calculus 做干预与反事实推断。
- **工业界真实用法是"混合式"**：专家给**骨架**（哪些边可能存在）⇒ 数据给**方向与强度**（这条边是否显著、多强）。**纯自动发现几乎没人敢用于生产决策**。
- **成熟开源（这一支的开源生态是全场最好的）**：

| 项目 | 定位 | 与本项目的关系 | 置信 |
|---|---|---|---|
| **DoWhy**（微软）+ `dowhy.gcm` 的 anomaly attribution | 因果推断四步法 + **反事实/异常归因**（Shapley 式） | ★ **直接对口** D-6「可能根因集合 + 排序」 | ✅ |
| **causal-learn**（CMU） | PC/FCI/GES 等经典结构学习 | 用真实指标序列做**边存在性辅助验证** | ✅ |
| **gCastle**（华为诺亚） | NOTEARS / GraN-DAG 等可微结构学习 | 同上，工业血统 | ⚠ |
| **Tigramite**（PCMCI+） | **时序**因果发现 | 指标时间序列最合适的一个 | ✅ |
| **CausalNex**（QuantumBlack） | 贝叶斯网结构学习 + 领域知识注入 | "专家骨架 + 数据定权"的现成实现 | ✅ |
| **pgmpy** | 贝叶斯网络推理 | 条件概率传播的轻量实现 | ✅ |

- **必须防的坑**：指标采样间隔不齐、自相关、非平稳（大促/月结流量）、混淆变量 ⇒ 伪边。**结论：用它做"边的验证与定权"，不要用它做"边的生成"**（本项目 `10-` §7 已把采样间隔 > 600 s 作为硬前置，方向一致）。

### 2.3 P3 · 知识图谱 / 本体 + 规则推理（★ 本项目方案1/方案2 所在）

一个可能反直觉的判断：**在电信、银行这类强标准行业里，这一支反而是最成熟的**，因为它是**标准驱动**而非数据驱动。标准谱系（比"选哪个图库"重要得多）：

| 标准 | 覆盖 | 与本项目的关系 | 置信 |
|---|---|---|---|
| **ITU-T X.733 / X.736** | 告警语义与告警关联 | 跨层告警关联的原始标准 | ⚠ |
| **ITU-T M.3010 / M.3400** | TMN 故障管理 | 同上 | ⚠ |
| **TM Forum SID + eTOM** | 共享信息/数据模型 | ★ 建议 `04-`（本体方案）补一节"与 SID/X.733 的对齐清单" | ✅ |
| **IETF YANG / OpenConfig** | 网络与设备层建模 | 本项目明确不做网络设备（`00-` §1.3） | ✅ |
| **OpenTelemetry Semantic Conventions** | 云原生"统一事实层"事实标准 | ★ 见 §3 | ✅ |
| **RDF/OWL/SHACL 栈** | 本体表达与约束 | 方案2 的载体（`04-`） | ✅ |

- **推理/校验栈（成熟度排序）**：GraphDB（Ontotext，RDFS+/OWL2 推理 + SHACL）、Apache Jena、RDF4J、Stardog（商业）；OWL reasoner：HermiT / ELK / Openllet / Konclude；SHACL：pySHACL、TopBraid。**本项目已有实测代价记录**：`10-` §6 第 ⑧ 条的结论是"完整 OWL 2 RL 闭包 > 9 分钟不收敛 ⇒ 改用按 `owl:inverseOf` 定向物化"——这与业界"别把运维本体当定理证明器用"的经验**完全一致**，是有价值的自有证据。
- **工业界的落地经验（值钱）**：纯 OWL DL 推理在运维场景常"算得出但没信息量"。真正产出价值的是 **SHACL 约束 + SPARQL 视图 + 规则引擎** 三件套——把知识图谱当**受约束的查询加速器 + 一致性守门人**，而不是推理机。本项目方案3（KG 直引 + 仅 4 工具）与 `04-` 的 T11b 档位裁定，方向与此一致。
- **商业对标（说明该支的成熟天花板）**：IBM Cloud Pak for AIOps（本体 + 拓扑 + 因果）⚠、ServiceNow ITOM/Event Management（CMDB 本体 + 事件关联引擎）✅、Moogsoft / BigPanda（事件关联与聚合）⚠。

### 2.4 P4 · 多模态时序 / 日志 / Trace / **Profiling**

| 类别 | 成熟开源 | 置信 |
|---|---|---|
| 时序异常检测 | **Merlion**（Salesforce）、**PyOD**、**ruptures**（变点）、sktime、statsforecast | ✅ |
| 日志 | **Drain3**（日志模板挖掘，工业级）、**LogPAI / loglizer**（日志异常检测，学术系但被广泛复用） | ✅ |
| Trace | OpenTelemetry、Jaeger、Grafana Tempo | ✅ |
| **持续 Profiling** | **Pyroscope**、**Parca**（eBPF 采样） | ✅ |

★ **这里要点出本项目当前结构的一个缺口**：四层的证据链到"慢 SQL / 会话等待事件"就到底了，**缺"应用代码/方法级"证据**。业界补这一层靠**持续 profiling**，它把"DB 慢"与"应用哪段代码在放大它"连起来。跨层 RCA 的"最后一公里"通常输在这里。本项目 `00-` §1.3 已把 app 探针列为非目标的一部分范围（N2 走 SSH 读 JMX/日志），**不在本批引入 profiling**，但应在报告"能力边界"里如实声明这一层缺失。

### 2.5 P5 · 变更与事件关联 ★（工业界**命中率最高**的根因类别）

- **结论**：Google 的自动化事故根因工作把**变更事件作为第一类根因候选**，用历史事故学习排序 ⚠[出处待核实]；行业经验同样指向"**大多数生产事故的根因是变更**"（发布、配置、容量、DDL、参数）。
- **开源**：Argo Rollouts / Flagger（金丝雀 + 自动分析回滚）、Keptn、GitOps（Argo CD）提供的变更时间线、Chaos 平台的 experiment 记录。商业对标：Datadog Change Tracking、Harness。⚠[版本与许可待核实]
- **与本项目最直接的缺口**：`01-` §2 的对象目录（四层 12 个可实例化类型）里**没有** `Change` / `Deploy` / `ConfigChange` 类对象。⇒ 跨层 RCA 缺变更维度会**系统性漏掉命中率最高的一类根因**。建议见 `docs\项目下一步优化方案建议.md` 的 P4（含"零契约风险"的降级做法）。

### 2.6 P6 · 图学习（GNN）

- **方法/代表**：基于因果图 + 图注意力的 RCA（`CausalRCA`、`RCD` 等 ⚠）；工具库 PyTorch Geometric / DGL / CogDL / OGB ✅。
- **落地判断**：学术 F1 漂亮，但**依赖标注故障数据集**；生产上标注稀缺 ⇒ **不建议作为主模型**，最多作为排序器的一个特征。
- **与本项目的关系**：本项目 `00-` §1.3 未包含，**建议保持不引入**（理由见 §7 坑 2）。

## 3. 标准与语义约定（跨层事实层的行业标准）

★ 这一节是"CCF 该向谁对齐"的答案，**成本低、收益直接**（便于公开基准数据映射进来，也便于银行侧与既有监控对接）。

| 标准 | 它约定什么 | 它**不**约定什么 | 与 CCF 的关系 | 置信 |
|---|---|---|---|---|
| **OpenTelemetry Semantic Conventions** | 属性/资源/span 的**命名与层次** | **层间因果** | ★ 建议 CCF 的**字段命名**向它对齐；因果层仍由本项目自建 | ✅ |
| **Elastic Common Schema (ECS)** | 日志/事件字段命名 | 同上 | 同上（可选参照） | ✅ |
| **OpenMetrics / Prometheus exposition** | 指标命名与类型 | 语义层次 | 同 OTel | ✅ |
| **TM Forum SID** | 资源/故障/告警/SLA 的信息模型 | 具体查询语言 | ★ 方案2 的"行业标准对齐"依据 | ⚠ |
| **ITU-T X.733** | 告警的语义字段与关联 | 云原生实体 | 同上 | ⚠ |

> ★ 对齐的**边界纪律**：向 OTel 对齐的是**命名**，不是**契约结构**。本项目 `01-` §1.1 已确立"中性名 → 载体名映射写在 `shared\mapping\*.yaml`，是数据不是代码"⇒ 命名对齐**只需改映射表与 `ccf.schema.json` 的字段名**，不触碰投影器代码。这使该项成为**成本最低的对外可比性改造**。

## 7. 必须防的六个坑

| # | 坑 | 为什么 | 本项目现状 |
|---|---|---|---|
| 1 | **纯数据驱动因果发现** | 采样不齐 + 非平稳 + 混淆变量 ⇒ 伪边 | 尚未做；若做，只能做"验证与定权" |
| 2 | **GNN 类方法当主模型** | 依赖标注故障数据集，生产标注稀缺 | 未引入（建议保持） |
| 3 | **让 LLM 直接读遥测** | OpenRCA 的核心发现 ⚠：无工具时定位能力很弱 | ✅ 已规避（工具面 + 有界载荷） |
| 4 | **多 Agent 协作** | 收益不确定、成本与不确定性放大 | ✅ 已裁定单 Agent（D-7），但文档未把 mABC 类工作列为"已知对照" |
| 5 | **借别人的分母** | 本项目 D-2/D-5 已明确拒绝 | ✅ 已规避 ⇒ P3 引入外部基准时必须标为**外部参考**、不进主判据 |
| 6 | **"跳数"当"因果强度"** | 9 跳拓扑是**可达性上限**，不是传播概率 | ⚠ 裁决已撤回边上的 `probability`/`weight` 等 5 个字段 ⇒ 现在排序口径是确定性的（满足判据数↓→跳数↑→关系优先级↓），**必须与跳数解耦**，否则"路径长但强因果"会被系统性压后 |
